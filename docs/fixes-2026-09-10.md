## 下一轮必须明确解决的边界

1. **Run 生命周期与恢复**：目前取消/错误的部分 assistant 内容仍未作为可恢复 Run 保存。增加 run_id、状态、检查点和中断恢复；编辑当前采用截断分支，尚无保留分支/撤销机制。
2. **工具执行边界**：当前同步工具无法被外层 async cancellation 抢占。引入异步工具接口、独立进程/超时/权限/输出限制，再添加文件和 Shell 工具。不要把 `spawn_blocking` 当作可杀死工具的方案。
3. **跨进程一致性**：互斥锁限于当前进程/ChatFeature 实例。多个 llmn/llmnt/桌面进程共用数据目录仍可能覆盖；应统一单实例 Runtime 服务或采用数据库事务与乐观锁。配置文件也可能与外部编辑器发生竞争。
4. **真正稳定的消息 ID**：现在仍以 m-index 配合 updated_at 版本保护编辑；反馈和其他未来操作也应统一采用持久化 MessageId + revision。
5. **设置与错误体验**：GUI 模型在开始聊天时保存；仅在界面切换但尚未发送的选择，以及 temperature 等完整设置持久化仍需补齐。启动连接失败应提供可重试的错误界面。
6. **安全部署范围**：本地 Host/Origin 防护不等于用户认证；当前服务适用于本机。公开/多用户部署需要独立鉴权、授权和密钥存储设计。
7. **协议一致性**：补充每种协议的限长结束、思考签名、工具失败等契约测试，以及少量可选真实端点冒烟测试。历史 Anthropic 用量采用旧语义，本轮没有重写历史数据。
8. **桌面发布与性能**：在 MSVC 工具链验证安装包和真实 WebView；继续按需加载语法高亮/数学渲染，降低主包。当前只有组件级/适配器测试，未做完整 GUI 自动化验收。

建议顺序：先完成 Run/工具的可靠执行与恢复，再选择一个具体用户工作流验证价值；暂缓新增前端、供应商数量和泛化插件架构。现有架构可以继续使用，不需要为本轮问题整体推倒重写。
