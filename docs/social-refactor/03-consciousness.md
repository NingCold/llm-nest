# 03 意识系统（Consciousness）

[总纲](README.md) · [聊天与消息](02-conversations-and-messages.md) · [AI 执行](05-ai-execution.md)

本文维护所属模块的规则与扩展目标。 实施状态见 [已完成](completed.md) / [尚未完成](pending.md)，当前调用契约见 [API 与事件](07-api-and-events.md)。

## 0. 名称与定义

本项目将软件管理的近期上下文、窗口摘要、长期记忆、跨窗口召回、来源追踪与遗忘机制统称为“意识系统”，英文为 **Consciousness**。其任务是让一个稳定 AI 身份在不同场合取得相关、允许使用且可修正的共同经历，并为每次运行准备上下文。这里的“意识”是工程系统名称；产品说明使用上述定义，不以命名声称 AI 具有主观体验。

文档统一写“意识系统（Consciousness）”，代码使用 `consciousness`，服务为 `ConsciousnessService`。消息、档案、MemoryRecord、ConversationSummary、ContextReference 和 ContextSnapshot 保留各自含义，不新增 ConsciousnessId。

## 1. 职责与边界

意识系统统一负责为确定的 AI、空间和运行选择背景，维护可追溯的摘要与记忆，并处理修订和遗忘。当前 ConsciousnessService 位于 `features/social/src/consciousness.rs`，由 SocialFeature 持有；下面的目录拆分是后续职责规划；中立领域类型放在 `crates/social/src/consciousness.rs`。不新增独立 Feature、Runtime 或数据库。

聊天历史不是全部长期记忆。角色背景由账号管理员维护，消息保存发生过的交流，记忆保存经过确认或有明确依据的结论。三者保留来源与不同的更新规则。

### 1.1 内部组件

| 组件 | 目标落点 | 职责 |
| --- | --- | --- |
| ConsciousnessService | consciousness/mod.rs | 对社交用例提供统一服务，协调下列组件 |
| ContextBuilder | consciousness/context.rs | 按目标 AI、空间、版本与预算准备请求材料 |
| Recall | consciousness/recall.rs | 筛选近期历史、有效记忆与明确的跨窗口引用 |
| Summary | consciousness/summary.rs | 按窗口分段生成、读取与失效摘要 |
| Memory | consciousness/memory.rs | 简单条目的创建、修改、确认与遗忘 |
| 后台巩固 | 后续再确定内部模块 | 自动提取、时效更新与角色记忆概览，参考 Dreaming |

完整消息仍由聊天用例写入 SocialStore，档案由身份用例维护。意识系统读取这些权威来源，不能复制一套独立聊天记录或把 AiProfile 当成自动生成的记忆。来源与权限筛选贯穿各组件，最终提交使用存储层原子版本校验。

ParticipationService 决定谁发言、何时等待和结束，Execution 负责模型与工具调用，Runtime 注入资源并托管生命周期。意识系统为已选定的运行准备材料；摘要和未来后台巩固不会自行创建社交发言、联系意图或工具授权。

### 1.2 分阶段范围

| 阶段 | 意识系统交付 |
| --- | --- |
| M0 | 确定来源、范围、摘要、记忆与快照类型及存储约束 |
| M1 | 基本上下文构造：身份档案、空间成员身份、近期原文、预算与来源快照 |
| M2 | 简单显式记忆、窗口分段摘要、群聊接续私聊、失效与遗忘、详情管理 |

M1 已需要基本上下文，M2 完善意识系统；复杂后台机制不作为 M0–M3 的完成前置。以下信息层次描述完整首版目标，不代表各层都必须在 M1 实现。

## 2. 意识系统的信息层次

组织原则是：**窗口保存经历，AI 账号持有记忆，每次发言临时组织上下文。** 同一群中的 AI 可以各自拥有不同记忆；窗口摘要则是同一来源范围内可共用的压缩材料。长期记忆跟随稳定账号，不跟随模型或某一次请求。公开资料、管理员维护的角色设定、原始消息和记忆各自保存，自动整理不能改写人格。

| 层次 | 用途 | 更新方式 |
| --- | --- | --- |
| 完整窗口记录 | 保存交流原始依据，供翻阅和按权限检索 | 每条消息提交保存，摘要不删除原记录 |
| 最近消息 | 理解当前话题、回复对象和连续输入 | 按可见范围与 token 预算选取 |
| ConversationSummary | 压缩较早讨论、未完成话题与约定 | 后台生成，追踪覆盖的消息及版本 |
| MemoryRecord | 保存关系偏好、明确事实和共同经历 | 手动创建或候选确认，支持修订与遗忘 |
| AiProfile | 表达角色背景、性格与风格 | 获授权管理员显式修改档案版本 |

首版没有外部知识库和通用 RAG 产品。优先用结构化筛选、近期内容和摘要，全文或向量检索在验证实际召回问题后引入；中文检索效果必须单独验证。

### 2.1 近期上下文由谁维护

软件保存聊天记录和可见范围；意识系统维护摘要、记忆及所选消息引用，内部 ContextBuilder 在每次生成前准备材料。模型的上下文窗口是本次输入、输出及协议所需内容的容量限制，按模型能力设置预算并预留输出空间。

M1 执行层先根据 AI 的绑定分配输出预算，再交给意识系统。显式 max_tokens 按原值预留，不压回 1024；留空时回答预算取 1024 与窗口四分之一的较小值，若当前 Anthropic 思考模式使用独立预算则加上该预算，最后受模型输出能力限制。输入预算为窗口容量减去实际输出预留。近期历史可按预算选择，完整原记录保留；角色与空间信息、当前触发消息及回复对象无法容纳时返回 budget_exhausted，不截断必要原文。参数边界见 [生成参数记录](m1-generation-parameters.md)。

首版不依赖模型在两次调用之间永久保留聊天，也不要求在软件中常驻一份模型内部状态。每次请求从权威存储与固定版本重新构造，缓存仅用于优化。provider 支持续接或压缩时，可以作为协议层优化，不能成为跨供应商记忆的唯一来源。[OpenAI 会话状态说明](https://developers.openai.com/api/docs/guides/conversation-state)

### 2.2 一个 AI 在多个窗口中的上下文

逻辑范围为 (ActorId, ConversationId)，本次 AiRun 再记录该范围下的 ContextSnapshot。角色默认在所有空间使用自身 ExecutionBinding，但每次请求中的内容独立。

例如“小林”与用户的私聊、读书群、创作群分别拥有独立的近期消息和摘要。读书群内所有当前成员共享完整群历史，每个 AI 带入自己的档案。是否发言由参与服务独立决定；本次请求按回复对象和容量选择材料。私聊与群、群与群不共享 provider 续接 ID，也不会自动合并成一条上下文链。

窗口与角色身份可以长期存在，一次请求的上下文则有有限容量。窗口分别构造请求，同时支持引用允许使用的跨窗口历史；跨窗口引用不合并聊天记录，也不共用 provider 续接链。

### 2.3 从群聊接续到私聊

目标私聊的请求由当前私聊内容，加上与当前话题相关、允许引用的群聊片段组成。例如用户和“小林”刚在读书群讨论第三章，用户在群消息上选择“与小林私聊继续”，软件打开小林唯一私聊，把所选消息及必要前后文作为带来源的引用。接下来的私聊回复可以沿该话题继续使用引用，但不会把整群历史长期挂载到这个私聊。

M2 先实现明确的消息/话题引用。用户直接说“继续刚才读书群的话题”时，可用群名、时间、回复关系等确定来源；无法唯一确定时请求澄清，不让模型猜一个群。后续再评估在允许的共同历史中自动召回相关话题，不以复杂全局检索作为首版前置。

自动接续的来源必须同时处于当前用户和目标 AI 的可见范围内，并在构造请求及提交回答时复核当前权限、来源版本和撤回状态。AI 不是当前群成员时，不能因为用户能查看就自动读到；用户可以明确转发自己有权分享的选中内容，在私聊中产生新的共享消息。私聊继续产生的内容不会自动回传到群。

跨窗口片段保留群名、发送者、时间和消息引用，区分“群里已讨论的内容”和“本次私聊新提出的内容”。引用源群摘要时，只使用符合这次话题和可见范围的摘要；需要精确细节时读取相关原文。

### 2.4 历史摘要的作用与归属

摘要将较早、已完整落盘的讨论压缩成较短内容，保留主题进展、重要结论、共同经历和未完成事项，使近期消息仍有前后背景，同时控制请求大小和重复发送成本。

例如早期数百条读书讨论可以压缩为“已经读到第三章；两人对某角色动机有不同理解；下次继续讨论第四章”，再与最近原文共同进入请求。摘要属于当前窗口，带覆盖范围与来源版本，不自动成为跨空间长期记忆。

摘要是有损材料，重要偏好与约定另外保存为结构化记录；询问具体原话时按权限检索原记录。首版采用可追溯的分段/增量摘要，保留原始来源，避免只对旧摘要反复改写而失去核对依据。

首版的聊天摘要按 Conversation 归属，不另外给每个 AI 建一份混合所有私聊与群聊的聊天摘要。一个窗口可有多个分段和版本；当前群成员可共用本群摘要，新加入成员也可读取加入前的群讨论。摘要只概括本窗口记录，不混入成员私聊。

同一 AI 使用统一的意识系统机制，各请求仍按 (ActorId, ConversationId) 构造。窗口摘要可以在来源范围相同的参与者之间复用；统一系统不意味着这个 AI 只有一个跨所有空间共用的模型上下文窗口。

未来可以在联系人详情提供“这个 AI 对我和共同经历的记忆概览”，汇总允许使用的记忆条目。它是面向特定关系与用途的视图，与窗口摘要分开；其内容不能不加区分地带入这个 AI 参加的所有群。

### 2.5 摘要什么时候生成与读取

第二批已接入按窗口启用的自动摘要。默认关闭，当前窗口成员在详情中明确选择摘要专用 provider/model、思考强度和输出上限后开启；不会继承任何 AI 的执行绑定或全局 Harness 参数。配置保存在 SocialStore 的 SummarySettings，服务端校验模型与预算；开启会产生独立模型调用。

每次聊天接话队列处理结束、开启设置或手动请求时检查较早的 committed 消息。最近 12 条继续使用原文，较早的未覆盖消息达到 16 条，或其保守输入估算达到摘要输入预算时，自动整理下一段。每段最多 32 条，并按摘要模型输入容量缩小；分段停在尚未完成的生成消息之前，避免其后续提交落入已概括范围；单条也不能容纳时保存明确失败，不截断原文。手动“整理下一段”可处理不足 16 条的较早部分，但仍保留最近 12 条。原文不足时不调用模型。

摘要后台全局并发为 1，每次唤醒最多处理 4 段，每次请求最长 120 秒；输出上限显式保存（最多 16384 tokens），正文另限 16384 UTF-8 字节，输入源集合最多估算 64 KiB。预算使用与聊天相同的保守 UTF-8 字节估算，另预留提示词开销，不能当作精确 tokenizer 或费用统计。失败、失效和中断分段须手动重试，不因后续新消息反复调用。更早的大批历史可在后续消息或手动整理时继续处理，不引入周期常驻整理器。

读取发生在每次 ContextBuilder 构造请求时。存储返回当前窗口、触发消息之前最近最多 64 个 ready 分段；近期原文完整可容纳且没有更早摘要覆盖的记录时跳过摘要。需要压缩或存在近期读取范围之外的背景时，保留当前问题、直接引用原文和显式记忆预算后，摘要最多占剩余输入的三分之一，优先较新的完整分段，再按时间排序。被选摘要覆盖的普通历史不重复输入，未覆盖近期记录继续用原文；当前问题和直接引用原文不被摘要替代。

ContextSnapshot 只登记实际使用的摘要 ID/revision，提交回答时复核分段有效状态和原消息版本。新增摘要仅影响新运行。关闭自动整理会停止未完成摘要任务，已有有效分段仍可被读取；重建失效分段重新读取当前原文，不对旧摘要反复概括。跨窗口摘要使用留待第三批。

摘要更新在后台执行，不把它的失败显示为聊天保存失败。没有可用摘要时继续使用预算内的原文；当前问题依赖尚未准备的早期细节时检索允许的原消息或说明信息不足，不能假称已经读取全部历史。

## 3. 数据与来源

完整目标的 MemoryRecord 字段：id、scope、owner_actor_id、subject_ids、kind、text、status、revision、created_at、updated_at、expires_at。

- scope 初版为 relationship(RelationshipId) 或 conversation(ConversationId)。范围不能通过修改字段直接扩大；共享应创建新的明确授权内容。
- kind 初版为 preference / fact / shared_experience / open_topic。
- status 设计为 candidate / confirmed / rejected / forgotten / stale；首个长期记忆版本只要求 confirmed / forgotten / stale，候选自动提取在后续加入。
- 来源通过 MemorySource 保存 message_id、message_revision，或记录 manual 作者与编辑 revision。摘要来源同样追踪依赖。
- 模型推断标注 inferred，不通过模型自报置信度自动升级为事实；confirmed 记录由谁、何时确认。
- open_topic 可以有期限和完成状态，不能无限期把旧任务当作待处理承诺。

ConversationSummary 保存 conversation_id、稳定的 sequence 覆盖范围、来源消息及版本、内容、status、revision、专用模型绑定、设置/发起者成员/参与版本、attempt、错误与创建/更新时间。status 为 queued/running/ready/failed/interrupted/stale；每段上的后台任务尝试与修订一起持久化，不创建聊天 AiRun 或 ParticipationPlan。一个窗口可保存多个分段与版本；复用时检查来源范围、版本和有效状态，读取时检查当前成员身份。派生索引不是权威数据，可以删除并重建。

ContextReference 保存来源 conversation_id、选中 message_id/revision 或话题覆盖范围、目标空间与 AI、发起者，以及关联的私聊消息。它是检索锚点，不授予超出原来源的访问权；引用共享与显式转发分别处理。ContextSnapshot 固定本次实际使用的来源及权限版本，跨窗口派生内容继续追踪这些依赖。

ContextScope 标识目标 ActorId + ConversationId。ContextSnapshot 包含实际使用的消息/摘要/记忆引用及版本、来源权限版本、档案/绑定/关系设置版本和预算信息，归属一次 AiRun。ConsciousnessService.prepare_context 返回运行期 PreparedContext：中立 common::Message 列表和 ContextSnapshot；持久化只保存需要的引用与版本，不另存完整请求副本。

## 4. 可见范围

关系记忆只在对应私聊中供该关系参与者使用。群记忆默认在源群内使用，并受当前成员身份约束；共同群聊的相关原文或摘要可以按 2.3 节引用到私聊，这不把整个群记忆库改成关系记忆。用户从聊天详情或联系人详情查看对应范围的本地记忆；用户拥有管理入口不授予某个 AI 读取全部记忆的权限。

筛选先根据 Actor、空间、成员状态、来源窗口与记忆状态执行，再做相关性排序；构造最终请求前复核。群摘要可以覆盖加入前的本群历史；私聊摘要或其他群摘要须分别检查来源空间。

首版不自动把私聊记忆带入群聊。用户主动发送或转发某段内容到群中，产生新的群消息来源；仅转发选中的内容，不给群 AI 开放原私聊记录。

任何模型输出都不能直接修改权限、确认记忆或授予工具能力。候选提取的输出先通过 schema、长度、来源和范围校验。

## 5. 记忆写入流程

M2 按三批交付：第一批显式记忆及其完整失效链路；第二批窗口分段摘要；第三批群话题接续唯一私聊。第一批不运行自动提取或后台巩固。

第一批以 AI 与聊天窗口为管理入口，服务端推导私聊关系范围或当前群范围，客户端不能扩大范围。当前窗口成员可以查看和维护该窗口中 AI 的显式记忆；管理员身份本身不授予其他窗口的读取权。创建和修改需要 AI 仍为当前成员，遗忘保留历史管理能力。联系人尚无私聊时先显式打开唯一私聊。

条目保存类型、文本、作者、创建/更新时间、版本和来源。来源为手动输入，或同窗口一条 committed 消息的确定版本；编辑时重新提交并核对来源，不能自动把过期引用升级为当前版本。第一批不实现独立主题实体、到期提醒或任务完成系统，open_topic 仅表示记忆内容类型；subject_ids、期限和自动候选留待后续有实际用例时扩展。

每次运行按当前 AI 和当前范围读取 confirmed 条目，优先最近更新的条目，在必要消息之后最多使用剩余输入预算的四分之一；单条不能完整容纳则跳过。记忆以带类型和时间的背景内容输入，不作为系统指令。来源快照只记录实际选中的记忆 ID 与版本，最终提交再次复核。此规则提供可预测的首版预算，不声称已实现语义相关性召回。

遗忘使条目立即退出读取，并清除记忆表及其修订记录中的正文，留下范围、来源和 forgotten 标记用于追踪与后续抑制。原聊天、已经发布的回答和数据库备份不随此操作删除。当前窗口摘要只依赖聊天原文，不读取显式记忆条目，因此遗忘一条记忆不连带删除原文摘要；撤回原消息会使对应摘要失效并清空派生正文。未来加入依赖记忆的摘要或索引时，必须参与记忆的失效链路。

首个长期记忆版本采用简单条目：内容、关系/群范围、来源、状态和版本。用户在聊天详情或联系人详情手动添加、编辑、遗忘，也可选择一条消息后明确“记住”。保存时复核范围与来源，成功后提交持久记忆变更引用；共享事件为 memory_changed，只含实体 ID 与版本。

首版不以复杂自动推断、向量索引、知识图谱或后台人格反思作为前置。长期记忆读取当前范围内有效条目；跨窗口背景按 ContextReference 单独筛选，模型输出不能自行确认一条长期记忆。

后续加入自动提取时：

1. 消息成功保存后，满足阈值的提取任务进入后台队列，不阻塞主要回答。
2. 提取只读取已经完成、允许使用的消息，中断草稿、工具原始日志和模型思考默认排除。
3. 校验结果后保存 candidate，附来源 revision 和范围。
4. 用户可以确认、编辑、拒绝；后台失败保持已保存聊天，单独提供任务状态。

摘要允许自动生成，但它是可失效的压缩材料，不应替代原消息来确认事实。用户可以检查摘要与来源。相关约定由结构化记录承载，不能只藏在一段摘要里。

摘要任务在生成前固定允许的来源版本，保存前复核。来源已变化时丢弃旧结果或标为 stale 后重新排队，不能覆盖更新的有效摘要。摘要保存/失效与 summaries_changed 持久引用事件同事务完成，详情页重新读取当前版本。源消息修改或撤回时，当前摘要与修订正文一并清空，来源引用与失效状态保留；新版本需明确重建。窗口参与状态或摘要设置改变会中断未完成任务，已完成摘要仍按当前成员关系读取。异常退出或正常关闭将 queued/running 收尾为 interrupted，重启不自动重放。

## 6. 检索与上下文构造

一次 ContextBuilder 输入至少包括 actor_id、conversation_id、bout_id、目标消息范围、可选 context_references、权限版本、档案与绑定版本、token 预算。

建议构造顺序：

1. 产品约束与本次参与指令。
2. AI 档案及明确的相处偏好。
3. 当前空间成员、时间与回复目标等必要信息。
4. 当前范围内有效的 confirmed 记忆与相关窗口摘要。
5. 本次接续话题需要的跨窗口引用、相关摘要和必要原文，复核来源可见性并标明来源空间。
6. 最近消息，保留发送者标签、回复关系和结构化提及。

显式关系设置优先于记忆中的表达偏好。群参与与工具权限始终由对应结构化设置决定，记忆或摘要内容不能覆盖这些控制。群聊请求不将私聊偏好原文作为公开材料。

消息引用、记忆文本和模型输出均作为内容，不能覆盖产品指令。来源 ID 和版本保存到 ContextSnapshot，实际 provider 请求不包含界面反馈、计时、运行状态或历史思考内容。

ContextSnapshot 记录用于审计与失效检查的引用和版本，默认不重复持久化完整请求正文。人格、记忆、成员和模型配置更新不能拼出来自不同版本的请求。

预算优先保留当前用户消息和必要协议配对；再保留直接相关的接续片段、记忆、近期消息与摘要。来源引用按相关性和预算选取，不因绑定到一条历史消息就永远进入后续所有请求。无法安全容纳时明确缩减或报错，不切断工具调用/结果配对。首版估算 token 的误差要通过不同协议离线测试说明。

## 7. 修订与遗忘

编辑来源消息：对应候选、来源支持的 confirmed 记忆与派生摘要标 stale，召回立即排除；记忆保留修改记录并要求重新核对，不继续作为旧来源支持的事实。失效传播覆盖跨窗口引用及其派生内容，不能只检查当前私聊的 context_epoch。

遗忘记忆：同事务标 forgotten、保留来源作为遗忘抑制标记、增加受影响上下文版本、提交变更事件；依赖该记忆的派生材料同步纳入失效清理；当前仅依赖原消息的窗口摘要遵守原文撤回规则。读取层在清理完成前就排除失效内容。

遗忘抑制记录保存作用域、被遗忘条目与来源版本，后续自动提取加入后必须阻止从同一来源自动提取回来。用户主动重新确认可以解除抑制。首版保留已知来源和遗忘标记，跨来源的语义等价识别需另行评估。

遗忘长期记忆与撤回原聊天是不同操作。前者移除该条目及其派生使用，不自动删除完整聊天记录；仍保留的原文可能在近期上下文或用户明确引用时被读取。若要求源内容也不再进入上下文，使用聊天用例撤回/清除对应来源。详情页明确显示这两个操作的范围。

正在使用被撤销记忆的运行收到取消请求，最终提交再检查版本，防止遗忘后又发布包含该内容的答案。已经发送到外部模型的请求不可撤回；界面不宣称遗忘能够删除供应商已接收的内容。

## 8. 后续长期记忆扩展

用户提供的 OpenAI 官方文章《Dreaming: Better memory for a more helpful ChatGPT》（2026-06-04）确认：Dreaming 在后台参考多段聊天来整理记忆，关注相关性、偏好约束与随时间更新；用户可以通过记忆概览查看和修改信息。该文章没有公开完整内部数据结构、任务触发阈值或召回算法。[OpenAI Dreaming 官方说明](https://openai.com/index/chatgpt-memory-dreaming/)

据此提出的本项目扩展方向是：后台整理允许使用的多窗口来源，更新过时事实，提供可编辑的角色/关系记忆概览，并按当前话题选择材料。去重、冲突处理、重要度、分层召回和共同经历组织属于本项目后续待设计方案，不能表述为 OpenAI 已公开的内部实现。

角色稳定身份不代表记忆可以跨所有空间公开。后台综合后仍保留每个结论的来源、使用范围、时间和版本；若混合了私聊与群聊来源，产物不能自动取得群可见权限。高级系统不得扩大原权限、恢复已遗忘内容或把推测当成事实。

复杂记忆系统不作为 M0–M3 的完成前置，也不在本轮创建空框架或实现自动“做梦”。后台模型调用仍需要明确绑定、预算和授权。

M2 的摘要任务与后续巩固任务都属于意识系统内部后台工作，由 SocialFeature 跟踪并在关闭时停止领取、取消与收尾。它们遵守并发、预算、来源校验与故障恢复；不使用 ParticipationPlan 或 ContactIntent 假装一次社交发言，运行详情与任务状态也分别展示。

## 9. 验收

1. 私聊记忆不会进入群聊请求，即使文本与群问题高度相关。
2. 新加入成员可通过本群摘要接续加入前的讨论；摘要不混入其他窗口内容。
3. 首个版本只读取当前范围内有效的显式记忆；后续推测停留为候选，拒绝、遗忘和 stale 记录不进入请求。
4. 编辑/撤回来源后，旧摘要与索引不能继续泄露该内容。
5. 遗忘标记重启后有效；后续自动提取加入时验证同一来源不会恢复该记忆。
6. 更换模型仍能找到关系记忆，记录的来源与权限保持不变。
7. 同一 AI 的私聊、群 A 和群 B 上下文分别构造，模型续接链不串用。
8. 生成摘要后原记录仍完整可读，摘要可以按来源重建与核对。
9. 后续提取失败不使已保存聊天回滚或重复生成回答。
10. 从共同群消息选择“私聊继续”，使用原唯一私聊，并带入相关片段的正确发送者、时间与来源；不带入其他群的无关历史。
11. AI 已退出源群或来源撤回/变更后，不能通过引用、旧摘要或缓存读到旧内容；显式转发只共享选中内容。
12. 新私聊消息不会自动回传源群；跨窗口派生材料不会绕过原有范围限制。
13. 短聊天不依赖摘要；分段摘要和未覆盖近期原文可接续；后台失败不撤销聊天保存，也不声称拥有全部历史。
14. M1 基本上下文可独立运行；M2 启用摘要与记忆不产生第二套 Runtime 或聊天历史。
15. 源版本变化时，迟到的摘要任务不能写入有效旧结果；摘要变更事件让详情读取当前版本。
16. 遗忘条目与撤回来源的范围可分别验证，不能将保留原文的遗忘操作显示为全部历史已删除。
