## 使用方式

聊天详情中的导出提供独立的“包含图片”和“包含文件”，默认均关闭。可以只带图片、只带普通文件，也可以两者一起；勾选任一项时下载 ZIP。解压后打开 chat.md 或 chat.json，图片在 images 中，普通文件在 files 中。未选择的附件只保留名称、类型、大小等说明。

失败保留格式和附件选项，可直接重试。Web 提示已开始下载；桌面仍使用系统另存为，写入成功后才提示已保存，取消单独反馈。文件导出不改变 AI 的能力，普通文件内容仍未交给模型读取。

## 内容和结构

```text
chat.md 或 chat.json
images/
  {消息ID}-{part索引}.png
files/
  {消息ID}-{part索引}/
    原文件名.txt
```

图片路径沿用原规则。普通文件按消息 ID 与 part 索引分目录，保留可用的原名称；同一消息或不同消息中的重名文件不会覆盖。旧无名或名称不可直接使用的附件使用 attachment.bin。附件原字节直接写入 ZIP，零字节文件也保留，不转码或解析。Markdown 的链接文字转义，目标路径按 UTF-8 编码，支持中文、空格、括号、# 和 %。JSON 的 filePath 是 ZIP 中实际相对路径，不包含编码后的 URL；记录中不序列化任何文件二进制。

记录 JSON 的 format 仍为 llm-nest.conversation：无附件选项为 v1，仅图片选项为 v2，启用普通文件选项为 v3。版本由导出选项决定，空窗口也可以导出。未选择的类型不附字节或 filePath。

## 读取和保存

SocialStore 在同一个只读事务中检查当前成员身份，读取完整窗口的当前消息与所选附件。正文、revision 和附件来自同一快照，不在事务后逐个重新查询。修订使用当前正文，撤回仅留占位；群话题引用只保留 ID/版本，不展开源群的正文或文件。历史修订、记忆、摘要、思考、内部角色设定和凭据不导出，已读状态和事件不变。SQLite 仍为 v13，无需迁移。

HTTP 的 includeImages/includeFiles 默认 false，任一为 true 返回 ZIP；均为 false 时保留原单文件响应。IPC 由共用客户端明确传入两项选择。桌面仍在原生对话框返回后复核访问权并读取快照，用现有临时文件写入、同步和替换流程保存。HTTP/IPC 共用格式化，未增加任意路径读取或写入能力。

ZIP 沿用现有内存生成方式，流式导出和大规模资源验收另行安排。此文件是窗口记录及选中附件，不是整库备份，不接入历史导入器。

## 构建清理与分工

按用户要求，使用 Cargo 按 profile 清理 target/debug、target/release 及 x86_64-pc-windows-msvc 下的对应编译目录。Cargo 合计报告约 110.7 GiB 文件，可用磁盘空间从约 23.9 GiB 增至 124.6 GiB；配置、聊天数据、验收日志/截图及安装程序未改动。本批验证关闭增量缓存和开发/测试调试信息，仅重新构建受影响包；这些是本次验证环境变量，没有修改项目构建默认值。计入本批重新构建后，可用空间约 121.8 GiB，净回收约 98 GiB；文件逻辑大小与实际回收磁盘空间分别计量。

GPT-6.1-Sol 分别完成前后端实现，主代理审核、执行端到端验收并统一文档。AGENTS 已明确要求主代理和子代理共同避免过度防御性编程：校验集中在输入、权限、存储和协议边界，内部沿用成立的不变量。本批复用现有快照、下载与保存流程。
